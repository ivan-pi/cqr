# API Design Document: `cqr_mkl_dormqr_compact`

> Assisted-by: Gemini:gemini-3.1-pro

## 1. Overview
This extension provides a routine to multiply a set of general matrices $C$ by the orthogonal matrices $Q$ (or $Q^T$) generated by the `mkl_dgeqrf_compact` factorization. It mirrors the standard LAPACK `ormqr` functionality but operates on batched matrices stored in Intel MKL's Compact format. This fills the gap between the compact QR factorization step and the application of the resulting orthogonal transformations. 

## 2. Syntax

```c
void cqr_mkl_dormqr_compact (
    MKL_LAYOUT layout, char side, char trans, 
    MKL_INT m, MKL_INT n, MKL_INT k, 
    const double * ap, MKL_INT ldap, 
    const double * taup, 
    double * cp, MKL_INT ldcp, 
    double * work, MKL_INT lwork, MKL_INT * info, 
    MKL_COMPACT_PACK format, MKL_INT nm
);
```

## 3. Description
The routine multiplies a set of general $m \times n$ matrices $C$ by $Q$ or $Q^T$ from the left or the right. The orthogonal matrix $Q$ is defined as a product of $k$ elementary reflectors, as returned by `mkl_dgeqrf_compact`. 

**Constraint Note:** Consistent with MKL's native compact ecosystem, this routine can only be called for groups of matrices that have identical dimensions (`m`, `n`, `k`), identical leading dimensions (`ldap`, `ldcp`), and the same storage format (`layout`).

Unlike ArmPL's `armpl_dormqr_interleave_batch` which explicitly requires batch, inner, and outer strides for data layout handling, this API abstracts those memory layouts behind the `MKL_COMPACT_PACK` parameter and the `MKL_LAYOUT` identifier, preserving perfect symmetry with MKL's native compact API.

## 4. Input Parameters

* **`layout`** (`MKL_LAYOUT`): Specifies whether two-dimensional array storage is row-major (`MKL_ROW_MAJOR`) or column-major (`MKL_COL_MAJOR`).
* **`side`** (`char`):
    * If `'L'` or `'l'`, $Q$ or $Q^T$ is applied to $C$ from the left.
    * If `'R'` or `'r'`, $Q$ or $Q^T$ is applied to $C$ from the right.
* **`trans`** (`char`):
    * If `'N'` or `'n'`, the routine applies $Q$ (No transpose).
    * If `'T'` or `'t'`, the routine applies $Q^T$ (Transpose).
* **`m`** (`MKL_INT`): The number of rows in each matrix $C$ ($m \ge 0$).
* **`n`** (`MKL_INT`): The number of columns in each matrix $C$ ($n \ge 0$).
* **`k`** (`MKL_INT`): The number of elementary reflectors whose product defines the matrix $Q$. 
    * If `side = 'L'`, $m \ge k \ge 0$. 
    * If `side = 'R'`, $n \ge k \ge 0$.
* **`ap`** (`const double *`): Buffer containing the elementary reflectors from the QR factorization, stored in MKL Compact format.
* **`ldap`** (`MKL_INT`): The leading dimension of each matrix within the compact buffer `ap`.
* **`taup`** (`const double *`): Buffer containing the scalar factors of the elementary reflectors, stored in MKL Compact format.
* **`cp`** (`double *`): Buffer containing the batch of matrices $C$ to be multiplied, stored in MKL Compact format.
* **`ldcp`** (`MKL_INT`): The leading dimension of each matrix within the compact buffer `cp`.
* **`lwork`** (`MKL_INT`): The size of the workspace array. If `lwork = -1`, a workspace query is assumed; the routine only calculates the optimal size of the workspace array and returns it in the first element of `work`.
* **`format`** (`MKL_COMPACT_PACK`): An MKL opaque structure containing batch and compact format metadata (vector length, packing format, etc.) returned by `mkl_get_format_compact`.
* **`nm`** (`MKL_INT`): The total number of matrices in the batch.

## 5. Output Parameters

* **`cp`**: Overwritten by the product of $Q$ (or $Q^T$) and $C$. The output data is also stored in Compact format.
* **`work`**: On a workspace query (`lwork = -1`), `work[0]` returns the minimum required `lwork`. This kernel is branch-free and needs no scratch, so that value is `1`.
* **`info`** (`MKL_INT*`): Intel MKL leaves the compact `info` unused/reserved, so its meaning is ours to define. For now we write a single scalar status, `0` on success -- an implementation choice that may change in future. The routine performs no argument checking (see section 6), so there is no `-j` illegal-argument reporting.

## 6. Design Considerations & Compatibility

1. **Naming Convention:** The `cqr_mkl_` prefix marks this as a routine supplied by the `cqr` project that is built on top of and alongside Intel MKL -- MKL-style in signature, but clearly not a native MKL call -- which also prevents linking collisions.
2. **Compact Format Abstraction:** Relying on `MKL_COMPACT_PACK format` ensures that the user's existing logic for packing matrices using `mkl_dpack_compact` remains strictly valid and reusable.
3. **Stride Agnostic:** Using `ldap` and `ldcp` within the compact buffer mimics standard LAPACK behavior and respects the inner working of MKL's compact vectorization routines.
4. **Padding and SIMD Semantics:** When the batch size `nm` is not evenly divisible by the SIMD vector length (e.g., $V=4$ for `MKL_COMPACT_AVX` or $V=8$ for `MKL_COMPACT_AVX512` in double precision), `mkl_dgepack_compact` pads the unfilled slots with identity matrices. Because the QR factorization of an identity matrix produces $\tau=0$ and empty Householder vectors, applying these padded transformations mathematically behaves as a no-op ($I \times C = C$). `cqr_mkl_dormqr_compact` can safely exploit this by executing unmasked SIMD instructions across the entire padded pack, ensuring maximum performance without corrupting trailing data.
5. **No Argument Checking:** Like MKL's own compact routines -- which "skip error checking for performance reasons" and make "the user responsible for passing correct parameters" (Intel MKL, *Numerical Limitations for Compact BLAS and Compact LAPACK Routines*) -- `cqr_mkl_dormqr_compact` validates nothing and assumes consistent inputs. Callers that want defensive parameter checking should use the portable `dormqr_compact`/`sormqr_compact` C API, which performs LAPACK-style `info = -j` validation.

## 7. Testing and Validation Methodology

Two test suites. The first isolates `cqr_mkl_dormqr_compact` against a known orthogonal transformation; the second checks it inside a full $AX=B$ solver pipeline built from MKL's compact operations.

### 7.1. Test Suite 1: Isolated Q Application ($Q^T B$)

Implement batched compact application of orthogonal reflectors. 

Input is a generated Householder representation `H` (a batch $\times$ `m` $\times$ `k` compact buffer containing reflectors below the diagonal), an associated `tau` array, and a target dense batched matrix `B` (batch $\times$ `m` $\times$ `n`). Datatypes are double precision (FP64). 

Return `B_out`, the in-place modified buffer resulting from `cqr_mkl_dormqr_compact(..., B)`. The checker explicitly materializes the dense orthogonal matrix $Q = I - V T V^T$ (or via dense LAPACK `dorgqr`), explicitly computes the dense reference `Q.T @ B`, and validates the LAPACK-style transformation residual `B_out - Q.T @ B`. 

This test specifically checks the correct application of the block reflectors independent of the factorization accuracy.

### 7.2. Test Suite 2: End-to-End Linear Solver ($AX = B$)

Validate the full $AX=B$ solution pipeline.

Input is a square matrix batch `A` (batch $\times$ `n` $\times$ `n`). To generate the right-hand sides `B`, the test either:
1. Generates a known ground-truth batch `X` and calculates `B = A @ X`.
2. Extracts specific columns of `A` to serve as `B` (in which case, the expected `X` contains standard basis vectors with a `1` at the selected row).

The solver pipeline executes:
1. `mkl_dgeqrf_compact(A)` to yield `(H, tau)`.
2. `cqr_mkl_dormqr_compact(H, tau, B)` to yield $Q^T B$.
3. `mkl_dtrsm_compact(H, Q^T B)` (using upper-triangular $R$) to yield the computed $\hat{X}$.

The checker reports the forward error $\hat{X} - X$ as well as the reconstruction residual $A @ \hat{X} - B$ as diagnostics. 

### 7.3. Input Data Distribution and Stress Testing

This shape set targets batched workloads typically found in sparse grid updates, small tensor inversions, and PDE local solves. Batched $32 \times 32$ up to $512 \times 512$ are specifically important.

Test and benchmark specs include a `cond` field. In this task, `cond` is a deterministic input-scaling knob, not an exact requested condition number: dense cases multiply columns of `A` by `logspace(0, -cond, n)`, so larger `cond` creates a wider dynamic range across columns. Additional stress cases feature specific structures: rank-deficient, near-rank-deficient, banded, row-scaled, near-collinear, upper-triangular, or clustered-scale inputs.

### 7.4. Correctness Gates

Correctness is a hard gate against standard dense LAPACK equivalents. Low-level optimizations (e.g., SIMD vectorization, cache blocking, or loop unrolling) are allowed only as internal implementation strategies: returned matrices must strictly satisfy the identical numerical invariants as the standard unbatched implementations. 

Residuals are measured in FP64 to reduce checker noise, and the target tolerance corresponds to the working precision (FP64). The numerical property tolerance is purely relative, with no absolute tolerance (`atol`). 
* For the isolated test, the hard gate is the application residual, evaluated with `rtol = 20 * n * eps`. 
* For the end-to-end solver, the hard gate is the relative forward error and the system residual, which uses `rtol = 100 * n * eps`, each applied to the corresponding matrix L1 norm. 

Among passing implementations, ranking is determined by runtime using the geometric mean of benchmark cases.

## 8. Implementation Strategy

The library implementation will be written in modern C++ (C++11/C++17) to leverage templating for layout and stride abstractions, while exposing the strict C API expected by the Intel MKL ecosystem via `extern "C"`.

### 8.1. API Boundary

The public-facing functions will act as C-linkage dispatchers. They will unwrap the `MKL_COMPACT_PACK` opaque structure to extract the vector length ($V$) and the number of packs, then dispatch to the appropriate internal C++ template instantiations based on `layout`, `side`, and `trans`.

### 8.2. Phase 1: Canonical Loop-Based Baseline

The initial implementation will serve as the ground-truth for numerical correctness. It will consist of explicit scalar loops over the compact packs, matrices within a pack, and the standard LAPACK Householder reflection algorithm elements. 

Given the compact layout, the iteration space generally follows:
1. Iterate over each pack (from $0$ to `npacks - 1`).
2. Extract the $V$-sized contiguous arrays representing matrix elements across the pack.
3. Apply the Householder reflection ($H = I - \tau v v^T$) scalar-by-scalar to each matrix in the pack.

This baseline guarantees the mathematical invariants are met and correctly handles the stride mapping (`ldap`, `ldcp`) without yet worrying about register pressure or vectorization.

### 8.3. Phase 2: SIMD Specializations

Once the canonical baseline is validated against the test suites, the internal kernel will be specialized into three progressively more aggressive SIMD tiers:

1. **Auto-Vectorization (`#pragma omp simd`):** Using standard OpenMP 4.0+ pragmas on the innermost loop (which iterates over the $V$ independent elements of a compact pack). This delegates the vectorization to the compiler while keeping the code entirely standard C++.

2. **GNU Vector Type Intrinsics:** Using GCC's `__attribute__((vector_size(N)))` extensions to define explicit vector types. This provides stronger guarantees than pragmas by forcing the compiler to treat the $V$ elements as a single register operand, while still abstracting away architecture-specific instruction names. *(Note: This approach is highly portable across GCC, Clang, and Intel compilers).*

3. **Explicit Hardware Intrinsics:** Direct usage of Intel intrinsics (e.g., AVX2 `_mm256_*` and AVX-512 `_mm512_*`). This tier will directly map the compact pack dimension $V$ to SIMD registers ($V=4$ for AVX2 double precision, $V=8$ for AVX-512). This provides absolute control over instruction scheduling, FMA generation, and memory alignment, extracting the maximum possible throughput for the target architecture.
